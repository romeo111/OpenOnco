Technische Spezifikationen

OpenOnco ist ein erstes Projekt. Jedes architektonische, klinische und Governance Detail wird in einem Markdown-Dokument unter specs/ that is versioned and open to public review. 10 active specifications cover everything from FDA non-device CDS positioning to the shape of every YAML entity in the KB. The full text lives at github.com/romeo111/OpenOnco/specs.

Quelle der Wahrheitshierarchie (von CLAUDE.md): Wenn Spezifikationen kollidieren, ist die verbindliche Reihenfolge 1. CHARTER.md → 2. Sonstige specs/*.md → 3. CLAUDE.Md → 4. Alles unter legacy/ ist nicht maßgeblich.

Aktive Spezifikationen (10)

Governance CHARTER.md

Charta und Governance

Project governance, scope (what it does and what it explicitly does not), FDA non-device CDS positioning (§15 with constraints C1-C7), the solo-maintainer workflow for source-traceable content (§6.1), patient-data privacy (§9.3), forbidden prompt patterns for LLMs (§8.3 — LLMs do not make clinical decisions).

Klinische CLINICAL_CONTENT_STANDARDS.md

Klinische Inhaltsnormen

Klinische Inhaltsstandards: Zitierformat (source_id + position + paraphrase + page), Evidenz-Level-Taxonomie (Tier 1-6), Rezensenten-Sign-off-Workflow, STUB → überprüfte Übergangskriterien. Jeder Anspruch in einer Indikation / Regimen / RedFlag Links zu einer Quelle Entity.

Lesen Sie auf GitHub → Rohe Markierung
Daten DATA_STANDARDS.md

Datenstandards — Patientenmodell

Datenmodell für Patientenprofil. FHIR R4/R5 + mCODE Ausrichtung auf der Roadmap. Codesysteme: LOINC + ICD-10/O-3 + RxNorm + CTCAE v5.0. Kein SNOMED CT und kein MedDRA im MVP (Lizenztore). Profilfelder und semantische Interoperabilität.

Lesen Sie auf GitHub → Rohe Markierung
Schema KNOWLEDGE_SCHEMA_SPECIFICATION.md

Spezifikation des Wissensschemas

Pydantic schemas for every KB entity — Disease / Indication / Regimen / Algorithm / Biomarker / Drug / Test / Workup / RedFlag / Contraindication / MonitoringSchedule / SupportiveCare / Source. Defines fields, validators, referential-integrity rules, and the migration roadmap to PostgreSQL.

Quellen SOURCE_INGESTION_SPEC.md

Quelle: Aufnahme und Lizenzierung

Wie wir Quellen aufnehmen: die Hosting-Matrix (referenziert vs gehostet vs mixed) mit H1-H5-Rechtsberechtigung, Lizenz-Klassifizierungsgates, die Add-a-Source-Checkliste (§8), die gehostete Checkliste ( §20) und das SourceClient-Protokoll für Live-APIs.

Ein synthetischer HCV-MZL-Referenzfall als P0-Akzeptanztest. Definiert jedes erforderliche Patientenprofilfeld (§2 Templates), die kritischen strukturellen Aussagen für Plan-Render-Ausgabe (§1.3) und Meilensteine M1-M6 zur Erweiterung der Abdeckung.

MDT-Orchester + Entscheidungsprovenz

Orchestrate_mdt Regeln (R1-R9 für die Behandlung, D1-D6 für die Diagnose), Rollenaktivierungslogik (erforderlich / empfohlen / optional), der Open Questions Mechanismus (Q1-Q6 + DQ1-DQ4 — der Motor weigert sich, ohne die erforderlichen Daten zu entscheiden) und ein Entscheidungs-Probediagramm für die Prüfungs-Grade-Erklärung.

Diagnose-Phase MDT (Vorbiopsie)

Pre-biopsy mode: when histology is not yet available the engine emits a DiagnosticPlan with a workup brief instead of a treatment Plan. CHARTER §15.2 C7 hard rule. DiagnosticWorkup + DiagnosticPlan schemas, generate_diagnostic_brief(), polymorphic orchestrate_mdt with DQ1-DQ4 rules.

Wie wir die Spezifikationen aktualisieren

Einzelprojekt. Eine verantwortliche Person veröffentlicht Aktualisierungen mit automatisierten Prüfungen und nachvollziehbaren Quellen. Externe klinische Prüfungen sind optional und werden gesondert dokumentiert.

Alle Spezifikationen sind ukrainisch-erste geschrieben (die Schnittstelle und die klinischen Prüfer sind UA), aber technische Begriffe und Lizenznamen bleiben in englischer Inline. Versionierung ist via git: jede Spec trägt v0.1 (draft) in der Kopfzeile und wird auf Moll / Major je nach Bruch Änderungen geschleudert.
