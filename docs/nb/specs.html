Spesifikasjoner

OpenOnco er et første prosjekt med spesifikasjoner. Alle detaljer om arkitektur, kliniske og styringer er satt inn i et nedslagsdokument under specs/ that is versioned and open to public review. 10 active specifications cover everything from FDA non-device CDS positioning to the shape of every YAML entity in the KB. The full text lives at github.com/romeo111/OpenOnco/specs.

Sannhetskilder (fra CLAUDE.md): når det oppstår konflikt, er bindende rekkefølge 1. CHARTER.md → 2. annet specs/*.md → 3. KLAUDE.md → 4. README.md. Alt under legacy/ er ikke autoritativ.

Aktive spesifikasjoner (10)

Styring CHARTER.md

Charter og styring

Project governance, scope (what it does and what it explicitly does not), FDA non-device CDS positioning (§15 with constraints C1-C7), the solo-maintainer workflow for source-traceable content (§6.1), patient-data privacy (§9.3), forbidden prompt patterns for LLMs (§8.3 — LLMs do not make clinical decisions).

Klinisk CLINICAL_CONTENT_STANDARDS.md

Standarder for klinisk innhold

Clinical content standards: citation format (source_id + position + paraphrase + page), evidence-level taxonomy (Tier 1-6), reviewer sign-off workflow, STUB → reviewed transition criteria. Every claim in an Indication / Regimen / RedFlag links to a Source entity.

Data DATA_STANDARDS.md

Datastandarder — pasientmodell

Patient profile data model. FHIR R4/R5 + mCODE alignment on the roadmap. Code systems: LOINC + ICD-10/O-3 + RxNorm + CTCAE v5.0. No SNOMED CT and no MedDRA in the MVP (license gates). Profile fields and semantic interoperability.

Skjema KNOWLEDGE_SCHEMA_SPECIFICATION.md

Spesifikasjon av kunnskapsskjema

Pydantic schemas for every KB entity — Disease / Indication / Regimen / Algorithm / Biomarker / Drug / Test / Workup / RedFlag / Contraindication / MonitoringSchedule / SupportiveCare / Source. Defines fields, validators, referential-integrity rules, and the migration roadmap to PostgreSQL.

Hvordan vi inntar kilder: vertsmatrisen (referanser versus vertsmod blandet) med begrunnelse for H1-H5, lisens-klassifiseringsporter, sjekkliste for add-a-kilde (§8), sjekklisten for verts-kilde(§20) og SourceClient-protokollen for levende API-er.

Referansetilfelle — «Småstor null»

Et syntetisk HCV-MZL-referansetilfelle som P0-aksepttest. Definerer alle påkrevde patientprofilfelter (§2-maler), kritiske strukturelle påstander for utgivelse av planer (§1.3) og milepæler M1-M6 for å utvide dekningen.

Orchestrate_mdt rules (R1-R9 for treatment, D1-D6 for diagnostic), role activation logic (required / recommended / optional), the Open Questions mechanism (Q1-Q6 + DQ1-DQ4 — the engine refuses to decide without the required data), and a decision-provenance graph for audit-grade explanation.

Pre-biopsy mode: when histology is not yet available the engine emits a DiagnosticPlan with a workup brief instead of a treatment Plan. CHARTER §15.2 C7 hard rule. DiagnosticWorkup + DiagnosticPlan schemas, generate_diagnostic_brief(), polymorphic orchestrate_mdt with DQ1-DQ4 rules.

Veiledning i programvare til støtte for FDA-Klinical Project

The official FDA guidance on non-device CDS classification under §520(o)(1)(E). Hosted under specs/ as a PDF. CHARTER §15 cites concrete criteria 1-4 from this document to justify OpenOnco's non-device positioning.

Hvordan oppdaterer vi spesifikasjonene?

Et solprosjekt. En vedlikeholder leverer oppdateringer med automatiske kontroller og kildesporbarhet. Ekstern klinisk gjennomgang er valgfri og registreres separat.

Alle spesifikasjoner er skrevet ukrainsk- first (grensesnittet og de kliniske reviewerne er UA), men tekniske vilkår og lisensnavn blir værende på engelsk i teksten. Versjonen skjer via git: every spec har v0.1 (draft) i overskriften og er knuffet på mindre/store avhengig av hvordan endringene brytes.
